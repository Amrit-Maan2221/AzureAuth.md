## 🚗 **The Story: Amrit Builds a Workshop App**

You work as a developer at **Maan Companies**, building a cloud app called:

> **Workshop Pro — a system for car workshops (B2B SaaS).**

Workshops use your app to:

* manage vehicles
* track mechanics
* create work orders
* send invoices

But there is one big problem…

### ❗ The app needs a way to **log in securely**

* Workshops want their **employees** to sign in
* Sometimes **other companies** (B2B clients) also want access
* The app needs permission to talk to other Azure services

Your manager says:

> “Let’s use **Microsoft Entra ID (Azure Identity)** instead of building our own login.”

And this is where our story begins…

---

## 🏢 **Step 1 — Registering the App: Creating Its Passport**

Think of your app like a **new employee joining a company**.

To let it enter the building, you must **register it** in Microsoft Entra ID.

When you register it, Azure creates:

1️⃣ **Application Object** — the **main blueprint** of your app
2️⃣ **Service Principal** — the **local identity** used inside a tenant

💡 Simple idea:

| Thing                  | Think of it as                               |
| ---------------------- | -------------------------------------------- |
| **Application Object** | The *blueprint file* of your app             |
| **Service Principal**  | The *ID card used inside a company (tenant)* |

---

## 🧩 **Single-Tenant vs Multi-Tenant (Two Worlds)**

Your boss asks:

> “Should only **our company** use the app, or can **other companies** use it too?”

You choose one:

### ✔ Single Tenant

Only **Maan Companies** uses the app
(only **one** service principal is created)

### ✔ Multi-Tenant

Other companies (client workshops) can also use it
A **service principal is created in each company’s tenant**

Just like:

* One blueprint (application object)
* Many ID cards in many companies (service principals)

---

## 🦸 **Meet the Service Principal — The App’s “Worker” in Each Tenant**

Whenever a company uses your app, Azure creates a **Service Principal**.

Think of it like this:

> Your app sends a helper worker into each customer’s company.

This worker:

* signs in
* decides what resources the app can use
* controls permissions

### 👷 Types of Service Principals (Simple)

| Type                 | Story Meaning                                             |
| -------------------- | --------------------------------------------------------- |
| **Application SP**   | Normal app identity inside a tenant                       |
| **Managed Identity** | Azure automatically gives identity to your API or web app |
| **Legacy SP**        | Old-style app from older systems                          |

---

## 🧠 **Why Do We Need It? (Real Use in Your Workshop App)**

Your app needs to:

* read workshop data from a database
* call Azure Storage to store photos
* update invoices via an API

But Azure first asks:

> “Who are you? Do you have permission?”

The **Service Principal answers**:

> “Yes, I am Workshop Pro, here is my ID, and these are my allowed actions.”

Then Azure allows or denies access.

---

## 🔗 **How Application Object & Service Principal Work Together**

Think of it like:

### 🏗 Application Object = Master Design

(one per app)

### 👤 Service Principal = Actual Working Copy

(one per tenant using the app)

Example:

* Your app exists globally → **Application Object**
* Workshop A starts using it → Azure creates **Service Principal A**
* Workshop B starts using it → Azure creates **Service Principal B**

Same app, different permissions in each tenant.

---

## 🎯 **Simple Real-Life Example**

> Workshop “AutoFix Garage” installs your SaaS app.

Azure does this automatically:

1️⃣ Reads your **Application Object** (blueprint)
2️⃣ Creates a **Service Principal in AutoFix tenant**
3️⃣ Gives it permissions (like:

* read vehicles
* create work orders)

Now your app works safely inside AutoFix’s environment.

---

## 🌟 **Summary in Super Simple Words**

* Registering your app = **giving it an identity**
* Application Object = **main blueprint**
* Service Principal = **working identity inside each company**
* Single-tenant → only your company
* Multi-tenant → many companies, many service principals
